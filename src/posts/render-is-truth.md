有些需求听起来是纯 UI 的，做起来才发现是个算法问题。

我遇到的一类是这样的：**某个东西必须跟「画面上实际渲染出来的样子」保持一致。** 不是差不多，是精确一致。

比如透明窗口的点击区域，比如拖拽时的边框高亮，比如滚动时的卡片阴影。我一开始的做法都是「在代码里再算一遍」，然后分别在小爪和 T2Video 里栽了同一个跟头。

## 一、点击区域：我以为算个矩形就行

小爪是一只桌面宠物，跑在一个无边框、背景透明的窗口里。

第一个撞上的 bug 不是动画不流畅，是**点不动桌面图标**：窗口多大，它就吃掉多大的鼠标事件。所以点宠物**旁边**的桌面图标，点在「空气」上，事件却被这个窗口收走了。视觉上是透明的，交互上是一堵墙。

最直觉的修法：告诉系统「只有这块区域属于我」。宠物在哪儿、多大，算个矩形：

```python
rect = QRect(px, py, w, h)
window.setMask(QRegion(rect))
```

能用，但只对静态姿态成立。宠物一开始动，问题就来了：

- **呼吸**（缩放） 尺寸每帧都在变
- **贴边侧躺**  包围盒方向变了
- **眨眼、换心情、挂未读徽章**  都会改变真正的可见像素
- **4 套形象**  身体轮廓本来就不是同一个形状

一旦「代码算的区域」和「实际画出来的像素」分叉，症状就是：**看得见的地方点不到，看不见的地方点得到**。而且它只在特定动画帧出现，最难查。

### 换思路：让渲染结果当唯一真相

```python
# 抓真实渲染结果  取 alpha 通道  逐行合并成矩形  交给系统
image = window.grabWindow()
region = self._region_from_image(image)
window.setMask(region)
```

关键在于**不再描述一遍形状**，而是直接去看像素。四步：

1. `grabWindow()` 抓一帧真实渲染结果，拿到 QImage
2. 取 alpha 通道，按阈值判断「这个像素算不算身体」
3. **逐行把连续的非透明像素合并成矩形**（span），组成 QRegion
4. `setMask(region)`  系统层面就不再把透明部分当作这个窗口

第 4 步是重点：这不是「在 Qt 里判断一下再把事件转发出去」，而是**系统层面就不认那块区域**。桌面图标能正常响应右键、拖拽、双击，性能也比自己转发事件好得多。

### 两个必须调对的参数

**alpha 阈值取 1，不取 0 也不取 128。**

- 取 0：抗锯齿边缘的半透明像素会留下几像素的缝隙，尾巴、耳朵尖会漏出「点不到」的空洞
- 取 128：边缘一圈不算命中，手感偏小，贴边时尤其明显
- 取 1：只要不是全透明就算身体  **用户看到一点点像素，就认为那里能点**，命中区跟视觉一致

**重建要节流，但漏一帧会掉手感。**

```python
interval_ms: int = 200          # 多久重建一次
min_apply_interval_ms: int = 200 # 两次应用遮罩的最小间隔
```

阈值本身是「每个不透明像素算不算」，这里的关键是**按行合并**：一帧 300×400 的宠物，如果每个不透明像素都变成一个 QRect，那是几万个矩形，`setMask` 会明显卡顿。按行合并成连续段之后，矩形数量掉到几百个量级  这是能顺畅跑的规模。

还有个兜底：抓帧失败时**恢复上一次的 region**，而不是清空。清空意味着整块窗口重新变成一堵墙，比形状旧一点糟糕得多。

## 二、同样的错误，换了个项目又犯一次

T2Video 里我要判断「生成的视频首帧跟参考图差多远」。

第一版的做法：**先把两张图各自算成一个数，再比这两个数。**

```python
# 错误做法：把两张图各自降维成一个标量，再比
score_a = some_hash(gray_a)
score_b = some_hash(gray_b)
if abs(score_a - score_b) > threshold:
    errors.append("首帧与参考图偏差过大")
```

这跟「算个矩形当点击区域」是同一个错误  **把一件需要精确对照的事，压缩成一个间接的近似。**

两张画面可能整体亮度差不多、但结构完全不同（一张是山，一张是水）；也可能结构相似、但亮度差一倍。任何「先各自降维再比」的做法都会丢掉这类信息。

### 这次直接对着两张图算

改成 **SSIM**（结构相似度） 它不降维到单个数再比，而是**在局部窗口上逐块对照**：

```python
def ssim(a, b, data_range=255.0):
    ga, gb = gray_of(a), gray_of(b)
    if ga.shape != gb.shape:
        gb = cv2.resize(gb, (ga.shape[1], ga.shape[0]))

    c1, c2 = (0.01 * data_range) ** 2, (0.03 * data_range) ** 2
    mu_a = cv2.GaussianBlur(ga, SSIM_WINDOW, SSIM_SIGMA)
    mu_b = cv2.GaussianBlur(gb, SSIM_WINDOW, SSIM_SIGMA)
    var_a = cv2.GaussianBlur(ga * ga, SSIM_WINDOW, SSIM_SIGMA) - mu_a * mu_a
    var_b = cv2.GaussianBlur(gb * gb, SSIM_WINDOW, SSIM_SIGMA) - mu_b * mu_b
    cov = cv2.GaussianBlur(ga * gb, SSIM_WINDOW, SSIM_SIGMA) - mu_a * mu_b

    num = (2 * mu_a * mu_b + c1) * (2 * cov + c2)
    den = (mu_a ** 2 + mu_b ** 2 + c1) * (var_a + var_b + c2)
    return float(np.mean(num / den))
```

公式里那三项分别对应：**亮度、对比度、结构。** 所以它同时看「亮不亮」和「长得像不像」，而不是把它们揉成一个数。

我甚至没用 scikit-image，自己用 numpy + OpenCV 写的  只为一个指标引入一个重依赖不划算。

## 三、三次踩的是同一件事

回头看，加上那篇「假指标」里的假验证，四次是同一类错误：

| 项目 | 我做了什么 | 应该做什么 |
|---|---|---|
| 小爪点击区域 | 在 Python 里重算宠物形状 | 直接取渲染结果的 alpha |
| 小爪拖拽高亮 | 用几何公式算边框位置 | 让边框跟随渲染坐标 |
| T2Video首帧对比 | 两张图各自降维再比 | 逐块对照（SSIM） |
| T2Video假验证 | 数轮廓当物体检测 | 报告能算出来的量 |

共同点：**我想用「一个更简单的模型」去代表真实情况，而不是直接去量真实情况。**

这类做法通常有三个诱因：

**一、直接测量看起来「贵」。** 抓一帧渲染结果、跑一次 SSIM，都比算个矩形、比个哈希慢。但那个「便宜」的方案要维护两份描述，代价在后面。

**二、闭式解看起来「优雅」。** 算个 QRect 多干净；抓像素多脏。但干净的解只在你假设的模型里成立，真实渲染会打脸。

**三、间接方案能给出「有结论」的答案。** 这是最危险的  轮廓数比关键词数，永远能得出一个大小关系。**一个恒能给出答案的错误指标，比一个偶尔失败的指标更坑。**

## 现在的判断标准

遇到「某个东西必须跟画面一致」时，我会先问一句：

> **我是在量真实情况，还是在用一个模型去代表它？**

如果是后者，就要问：**这个模型会不会和现实分叉？** 会分叉的话，分叉的那一天你能不能发现？

- 单个矩形  会分叉（动画一开始就分叉）
- 哈希对比  会分叉（换成结构不同但亮度相近的图就出错）
- 数轮廓  会分叉（任何非纯色图都能骗过它）

而 `grabWindow()` 不会分叉  **它取的就是真实画面本身**。SSIM 也不会  它逐块对照原地比较，没有中间模型。

**凡是能找到「直接测量」路径的，就别绕道建模。** 便宜的方案看起来省事，但你要为它维护一份永远追不上现实的描述。
