凌晨两点告警响了。我看过太多人在这种时候把最宝贵的十分钟用在错误的地方  比如打开 IDE 开始翻代码。

下面是我值班三年总结出的前 5 分钟动作顺序。它不能帮你立刻找到根因，但能保证你不把事情搞得更糟。

## 第 0 分钟：先确认真的是故障

告警不等于故障。误报的常见来源：监控口径改了、上游在做压测、采集器抖了一下、有人手动跑了数据订正。

先问三个问题：

1. **用户能感知吗？** 打开线上页面自己点一遍，比看任何图表都快。
2. **影响面多大？** 全量还是某个渠道、某个地域、某些用户？
3. **还在恶化吗？** 斜率比绝对值重要。

然后在群里第一句话就说清楚你在做什么：

```
[2:07] 我在看订单创建失败告警，10 分钟内同步结论。先不动线上。
```

不要发「有人在吗」或者「这个是不是有问题」 值班群里最贵的是确定性。

## 第 1 分钟：看最近变更

经验值：**大部分线上问题来自变更**。发布、配置、数据订正、依赖升级、甚至上游流量变化。

```bash
# 最近 2 小时的发布记录（换成你们平台的命令）
kubectl rollout history deploy/order-service -n prod | tail -5

# 最近改过的配置和开关
git log --since="2 hours ago" --oneline -- config/
```

如果 5 分钟前刚发过版，**回滚就是最好的排查手段**。你不需要先知道为什么。

## 第 2 分钟：止损，而不是找根因

这个阶段的目标只有一个：让用户不疼。常用手段按代价从小到大：

| 手段 | 适用场景 | 代价 |
| --- | --- | --- |
| 功能开关关闭 | 新功能出问题 | 极低，秒级生效 |
| 回滚发布 | 刚发版不久 | 低，几分钟 |
| 降级（返回缓存/默认值） | 下游依赖挂了 | 中，数据可能不一致 |
| 限流 | 被流量打垮 | 中，会拒绝部分用户 |
| 切流到备用集群 | 单机房问题 | 高，需要预案 |

**你做的每一个动作都要记时间线**，包括「打开开关」「关闭开关」这种看起来无关紧要的。

## 第 3 分钟：拉人，但要有结构

一个人闷头查 40 分钟是最糟的选择。但拉人也要有结构，否则群里会变成一堆「我也是」「试试重启」的噪音。

我的模板：

```
现象：订单创建接口 5xx 占比 12%，从 2:03 开始
影响：全量用户，支付渠道 B 不受影响
已做：2:07 回滚 order-service v2.14.3（进行中）
需要：@DBA 帮忙看下 orders 表是否有锁等待
```

三行话说清：**现象、影响、已做动作**，再点名需要谁。

## 第 45 分钟：把时间线写下来

在一个地方记录（频道置顶、共享文档都行）：

```
02:03 告警触发，订单创建 5xx
02:05 确认线上页面报错，影响全量
02:07 开始回滚 v2.14.3
02:11 回滚完成，错误率降到 0.4%
02:13 继续观察 10 分钟
```

为什么值得花这 30 秒？因为复盘时所有人的记忆都会扭曲。有了时间线，讨论才会围绕事实，而不是「我记得当时是不是你改的」。

## 四个反模式

**一上来就翻代码。** 除非你已经有明确假设，否则先止损。

**沉默排查。** 你在群里不说话，其他人就不知道要不要动手，最坏的结果是两个人同时改线上。

**改了线上不记录。** 复盘时说不清「到底哪一步恢复了」。

**血还没止住就讨论「如何避免」。** 先把火扑灭，复盘明天再说。

## 值班卡片

打印出来贴在显示器边上：

```
1. 确认真假：自己点一遍线上，看影响面和斜率
2. 看变更：最近 2 小时的发布 / 配置 / 数据订正
3. 止损：开关  回滚  降级  限流  切流
4. 同步：现象 / 影响 / 已做动作 / 需要谁
5. 记录：每个动作带上时间
6. 复盘放到明天，先止血
```

最后一句：**值班的目标不是当英雄，而是让系统平稳、让信息透明。** 你救了多少次火没人记得，但你把火扑灭前让大家知道现状，团队会一直信任你。
